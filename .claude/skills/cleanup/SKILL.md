# Skill: コードベース大掃除

## 概要
不要なプランファイル・gitkeep を除去し、todo.md・docs を本質的な内容のみに整理し、lessons.md を圧縮して優先度順に並べ替えた上で、lint/build/test の最終確認まで一気に行うスキル。
「コードからは読み取れない情報のみを残す」という `docs/README.md` の方針に従い、ドキュメントの冗長性を排除する。

## トリガー
ユーザーが `/cleanup` を実行した時

## 引数
- `<パス>` (任意): 対象スコープを限定する場合のディレクトリ（例: `/cleanup apps/api`）
- 引数なし: リポジトリ全体を対象とする

## 全体フロー

```
Step 1: プランファイル整理
Step 2: .gitkeep 整理
Step 3: todo.md 整理
Step 4: docs 整理
Step 5: lessons.md 圧縮
Step 6: lint / typecheck / build / test 検証
Step 7: 最終報告
```

各 Step の終わりに差分サマリーをログ出力し、承認を待たずに次の Step へ進む。誤削除を避けるため「迷ったら残す」原則は維持する。

---

## Step 1: プランファイル整理

### 目的
`.claude/plans/` 配下の「役目を終えたプラン」を削除する。

### 削除候補の判定
1. `ls .claude/plans/*.md` で全プランを列挙する
2. 各プランについて、ファイル名末尾の概要・本文を読み、直近の `git log --oneline -50` と突き合わせる
3. 以下のいずれかに該当するプランを **削除候補** として一覧化する:
   - プランの完了条件に対応するコミットが main 経由で取り込み済み
   - プラン作成日時より新しいコミットで同じスコープのリファクタが既に完了している
   - 「廃案」「再提案しない」等の判断記録がメモリ／コミット履歴に残っている
4. 判定に迷うものは候補に **含めない**（誤削除を避ける）

### 実施
判定で削除候補に挙がったプランをまとめて `rm` する。実行後、削除したファイル一覧をログ出力する。
- 判定に少しでも迷うものは候補に含めず残す（誤削除回避は判定側で担保する）

---

## Step 2: .gitkeep 整理

### 目的
ディレクトリの空状態を保つためだけの `.gitkeep` のうち、もはや不要なものを削除する。

### 削除候補の判定
1. `find . -name ".gitkeep" -not -path "./node_modules/*" -not -path "./.git/*"` で列挙
2. 各 `.gitkeep` について、同じディレクトリに **git 追跡されている他のファイル**（`git ls-files` で確認）が存在するものを削除候補とする
3. 追跡ファイルが `.gitkeep` のみのディレクトリは残す。特に gitignore 対象のファイルだけが同居するディレクトリ（`.claude/plans/`・`.claude/tasks/` 等）は、`.gitkeep` を消すと git 上でディレクトリ自体が消えるため必ず残す

### 実施
削除候補をまとめて `rm` し、削除した `.gitkeep` のパス一覧をログ出力する。

---

## Step 3: todo.md 整理

### 目的
`.claude/tasks/todo.md` は作業のたびに追記される高頻度更新ファイル。完了タスクの詳細が積もると、**未完了の項目が埋もれて一覧として機能しなくなる**。残すのは「まだ終わっていないこと」と「コードからは読み取れない知見」の2つだけにする。

### 判定
`## <見出し>` 単位で以下に分類する。

1. **完了セクション**（配下の項目がすべて `[x]`、または見出しに「完了」がある）→ **完了ログ1行へ圧縮する**
   - 形式: `- <日付> <見出し>（<主要コミット>）`
   - 対応コミットは `git log --oneline` で確認する。**コミットが見つからないものは完了と扱わず残す**
2. **完了セクション配下の知見**（`### 判断として残すもの` / `### 検証で分かったこと` / `### 〜が掘り当てた実バグ` 等）→ **移管先を確認してから処理する**
   - `.claude/rules/` / `docs/` / `.claude/lessons.md` に記載済み → 削除する
   - 未記載でコードから読み取れない → **移管する**（不変の方針・規約は `.claude/rules/`、設計判断の why は `docs/`、失敗から得た教訓は `.claude/lessons.md`）
   - どこに移すべきか判断が付かない → **todo.md に残す**
3. **未完了の項目**（`[ ]`）・「残課題」「積み残し」「ユーザー判断待ち」→ **必ず残す**。完了セクション配下にあるものは、消える前に未完了の集約セクションへ引き上げる
4. **存在しないファイルを指す行**（Step 1 で消したプランへの `プラン: .claude/plans/*.md` 参照など）→ その行のみ削除する

### 実施
圧縮後は「**未完了の集約セクション**（`## 残課題` 等）+ `## 完了ログ`（1行 × N）」の形に寄せる。知見を移管した場合は移管先ファイルも Edit する。反映後、圧縮した見出し数・移管した知見の件数・残した未完了項目数をログ出力する。

<important>
**未完了項目を消さない。** todo.md の圧縮で失うと痛いのは完了済みの記述ではなく、**完了セクションの中に紛れている未完了項目**である。セクションを消す前に、配下に `[ ]` が1つも残っていないことを必ず確認する。
</important>

## Step 4: docs 整理

### 目的
`docs/README.md` の方針（「コードからは読み取れない情報のみ残す」）に厳密に従い、冗長な docs を削減する。

### 削除・改稿の判定
各 docs ファイル（`docs/*.md`）について以下を行う:

1. ファイルを読み、コードから自明な内容（API シグネチャ、型定義の写し、ルーティング表、自明な手順書）を抽出
2. 以下なら **削除候補** とする:
   - 内容全体がコード（スキーマ定義・ルーティング定義・型定義等）から復元可能
3. **改稿候補** とするもの:
   - why / 非自明 UX / トラップ事例 / 運用ルール以外の節が混在しているもの → 該当節のみ削除
4. **rules 波及候補** とするもの:
   - docs の削除・改稿によって `.claude/rules/` の記述と矛盾が生じる、または rules が古い前提を指したまま取り残されるもの
   - docs から消した「不変の方針・規約」が rules 側に未反映で、本来 rules に置くべき内容

### 実施
削除候補は `rm`、改稿候補は Edit で反映する。`docs/README.md` の目次もあわせて更新し、反映したファイル一覧をログ出力する。
rules 波及候補があれば、対応する `.claude/rules/<file>.md` を Edit で整合させる（矛盾の解消・移管先の追記）。CLAUDE.md の参照テーブルに増減がある場合はそこも更新する。
判定基準を満たさない（why / 非自明 UX / 運用ルールが含まれている）ファイルは触らない。rules の更新は docs 変更との整合に必要な範囲に限定し、方針そのものの変更には踏み込まない（**迷ったら残す**）。

---

## Step 5: lessons.md 圧縮・並び替え

### 目的
`.claude/lessons.md` は作業のたびに追記される高頻度更新ファイル。放置すると重複・陳腐化した教訓が積もり、追記順のため**重い教訓が末尾に埋もれる**。**教訓の本質を保ったまま**冗長性を削り、**優先度順に並べ替える**。学びそのものは消さない。

### 圧縮の判定
`.claude/lessons.md` を読み、各エントリを以下に分類する:

1. **統合候補** — 同じ教訓を別の言い回しで述べている複数エントリ → 1 つに統合する
2. **削除候補** — 教訓がすでに恒久ルールへ昇格しているもの:
   - 内容が `CLAUDE.md` / `.claude/rules/` に規約として明記済み（lessons.md に残す必要がない）
   - 参照しているワークフロー・ツール・ファイルが現在は存在しない
3. **圧縮候補** — 教訓は有効だが文章が冗長 → 核心（何を・なぜ）だけを残して短縮する
4. **据え置き** — 上記に当てはまらない有効な教訓はそのまま残す

<important>
**圧縮は毎回・全エントリに掛ける。並び替えだけで済ませない。**

- **1エントリの目安は箇条書き2〜4行**（`<important>` 1つを含んでよい）。超えるものは「何が起きたか・なぜそうなるか・次に何を確認するか」の3点だけ残す
- **同じ結論を補強するだけの具体例は1つに絞る。** 数値・経緯・再現手順の詳細は削る
- **再発防止のトリガー**（いつ思い出すべきか・何を確認するか）は削らない。**削るのは経緯のほう**
- 節（`###`）を持つエントリは、節を畳んで箇条書きへ落とす
</important>

### 並び替えの基準

<important>
**上から優先度順に並べる。基準は「破ったときの損害 × 気付きにくさ」。**

| 帯 | 該当する教訓 |
|---|---|
| 高 | ユーザーの信頼・安全に直結するワークフロー規約（無断コミット等）／判断の土台になる思考の型（証拠の扱い・取りこぼしの作り方） |
| 中 | **型検査もビルドも通り、画面や実機を見るまで気付けない**種類の壊れ方 |
| 低 | 手戻りが小さく済む進め方・ツール固有の手順 |

帯の中では既存の並びを保ち、不要に順序を動かさない。**帯の見出しは作らず、`## N.` の連番のまま並べる**（帯は判断の道具であって、ファイルの構造ではない）。

**番号は並べ替えのたびに動く。** 他ファイル・他エントリから lessons を参照するときは**番号ではなくタイトル**で書く。
</important>

### 実施
- 統合・圧縮・並び替えを反映し、見出し番号は連番に振り直す
- 削除は「恒久ルールへ昇格済み」と確実に言えるものだけに限定する（**迷ったら残す**。教訓の喪失は再発を招くため誤削除のコストが高い）
- エントリ本文が他のエントリを番号で参照していたら、タイトル参照へ書き換える
- 反映後、統合 / 削除 / 圧縮した件数と各エントリの見出し、および並び替え後の順序をログ出力する

---

## Step 6: lint / typecheck / build / test 検証

掃除によって壊れていないことを確認する。実行コマンドはプロジェクトの定義（package.json / Makefile 等のタスクランナー設定、`.claude/rules/tech-stack.md`）から特定する。

- lint / typecheck / build / test に相当するタスクを順に実行する（プロジェクトに存在するもののみ）
- 各ステップは前段が失敗しても続行（全結果をまとめて報告するため）
- E2E テストはこのスキルでは実行しない
- 失敗があれば、原因が掃除によるものか既存の問題かを切り分けて報告する
- 掃除起因の失敗のみその場で修正し、既存の問題はユーザーに判断を委ねる

---

## Step 7: 最終報告

以下のフォーマットで集約してユーザーに返却する:

```markdown
# 大掃除結果

| カテゴリ | 件数 | 詳細 |
|---------|-----|------|
| プランファイル削除 | N | <ファイル名一覧> |
| .gitkeep 削除 | N | <ディレクトリ一覧> |
| todo.md 圧縮 | N | <圧縮した見出し一覧> |
| todo.md からの知見移管 | N | <移管先ファイルと内容> |
| docs 削除 | N | <ファイル名一覧> |
| docs 改稿 | N | <ファイル名一覧> |
| rules 更新 | N | <ファイル名一覧（docs 波及分）> |
| lessons.md 統合/圧縮 | N | <見出し一覧> |
| lessons.md 並び替え | - | <並び替え後の順序 / 基準> |
| lessons.md 削除 | N | <見出し一覧> |

## 検証結果

| チェック | 結果 |
|---------|------|
| lint      | OK / NG |
| typecheck | OK / NG |
| build     | OK / NG |
| test      | OK / NG |

### 失敗詳細（ある場合）
<エラー内容を簡潔にまとめる。掃除起因か既存問題かを明記>

## 残課題
- <掃除では対応しなかった項目（規模が大きすぎる等）>
```

## ルール

- **削除系は判定基準に従って自走実行する**。承認は求めず、削除/改稿したファイルはすべて Step 6 の最終報告に含める
- 「迷ったら残す」を原則とする。誤削除のコストの方が掃除漏れのコストより高い
- Step 1〜5 のいずれかで差分が発生した場合、Step 6 は必ず実行する
- E2E テスト・大規模な構造変更が必要になる修正は本スキルの対象外（別タスクとして提案する）
- 各ステップの実行前に、対象ファイル数が想定より多い（例: 50 ファイル超）場合はユーザーに確認する
