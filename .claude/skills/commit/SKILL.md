# Skill: コミットワークフロー

## 概要
conventional commit 形式でのコミットと、Codex レビューを組み合わせたワークフロー。

## 役割
コミットメッセージは **その変更時点の根拠** を残す場所。`docs/` と同様に「なぜこの変更をしたか（why）」を記録し、**直近の変更を時系列で追える**のが強み（`README.md` の「情報の置き場所と役割」参照）。

- コードコメントが「その場に居続ける実装の why」なのに対し、コミットメッセージは「変更（差分）そのものの why」を担う
- したがって body には *何を変えたか* だけでなく **なぜ変えたか** を必ず書く。差分を読めば分かる what の羅列で終わらせない

## トリガー
ユーザーが `/commit` を実行した時

## フロー
```
1. git diff --cached --stat で変更内容を確認

2. conventional commit メッセージを生成
   - type: feat / fix / refactor / chore / docs / style / test
   - scope: 変更対象のモジュール名
   - title: 簡潔な変更概要
   - body: 変更の詳細と **なぜその変更をしたか（why）**

3. ユーザーに確認を求める

4. 承認後コミット
```

## コミットメッセージフォーマット
```
<type>(<scope>): <title>

<body>
```

- コミットメッセージ（title・body とも）は **英語で記載する**

## 禁止事項
- 余計なフッター（`Generated with...`, `Co-Authored-By`等）は含めない（Claude Code がデフォルトで付与するフッターも対象。本テンプレートの意図的な上書きルール）
- 絵文字は使用しない
- ユーザー承認なしでコミットしない

## アトミックコミットモード

複数の論理グループの変更が混在している場合に使用する。

### フロー
1. `git diff --cached --stat` と `git diff --stat` で全変更を確認
2. 変更を論理グループに分類（機能追加、バグ修正、リファクタリング、設定変更 等）
3. 無関係な変更を検出した場合、ユーザーに警告
4. グループごとに:
   a. 該当ファイルのみステージング
   b. conventional commit メッセージを生成
   c. ユーザーに確認 → 承認後コミット

### 自動検出
`/commit` 実行時に複数の論理グループが検出された場合、アトミックコミットモードの使用を提案する。
